# 02 — 素材库规范

## 定位

素材库 = **所有会被复用的小说内容**，无论它是不变的还是变化的。它不是一张"设定表"——凡是后续写作可能再次引用、需要保持一致的内容，都应入库。

**原则：数据库中的内容以"agent 看得懂"为先。**

## 核心概念

- **条目（Entry）**：一个可复用的内容单元（角色/地点/道具/概念/场景模型/伏笔……）= 数据库中的一行
- **类型自由**：没有固定类型清单。agent 可以按需创建任何类型，创建时用 `type add` 登记含义
- **维度自由**：维度是属性分组（身份/外貌/场景模型/伏笔状态……），同样可自定义，用 `type add`（kind=dimension）登记含义
- **属性**：维度内的键值对。**一个键可以有多条描述（多行）**，每条描述是一个字符串

## types 表（类型字典）

所有自定义类型和维度都必须登记，保证换一个 agent / 新会话也能看懂：

```bash
python novel-cli/cli.py type add entry character "角色：有独立意志与成长弧的人物"
python novel-cli/cli.py type add entry scene     "场景模型：反复出现或需要固定布局的场所"
python novel-cli/cli.py type add dimension 场景模型 "该场景的空间布局、物件方位等固定描述"
python novel-cli/cli.py type add dimension 伏笔   "伏笔的埋设/揭示状态与条件"
python novel-cli/cli.py type list
```

`type add` 参数：`<kind>`（entry|dimension）、`<type>`（类型名）、`<description>`（一句话含义）。

## 三种内容形态

1. **不变内容（设定集）**：基础设定，一般在全书梗概构建阶段写入，用 `entry set`
2. **变化内容**：同一事物在不同阶段状态不同 → 用 `entry append` 追加多条描述，**用自然语言在文本里写明有效区间**，例如：
   ```
   （第1-5章）旧布局：收银台在入口左侧，货柜：零食/日用品/生鲜
   （第6章起）重新装修：收银台移到入口正中，新增冷柜区
   ```
3. **不确定是否复用**：先记一条"首现位置"描述（如 `首次出现：L3#12`），后续复用可查可跳转

## CLI 命令

```bash
# 条目操作
entry add    <type> <name>                     创建条目（type 自由，新类型先 type add 登记）
entry get    <name> [--type TYPE]              查看条目全部属性（多行描述逐行显示）
entry set    <name> <dim> <key> <value>        设置/覆盖单个属性值
entry append <name> <dim> <key> <value>        ★ 同一 key 追加一条描述（多行；区间写进文本）
entry del    <name> <dim> [--key KEY]          删除维度或单个属性
entry list   [--type TYPE]                     列出条目
entry search <keyword>                         搜索条目名或属性值

# 类型字典
type add     <kind> <type> <description>       登记 entry/dimension 类型的含义
type list                                     列出全部已登记类型

# 维护
export    [entries|plots|all]                  导出 Markdown
```

## 使用规则（重点）

**写 L3/L4 前**：
1. 列出涉及的角色/地点/道具/概念
2. 对每个条目执行 `entry get` 核查
3. 涉及反复出现的场景 → 查它的"场景模型"维度，核对布局描述，防止前后冲突
4. 涉及伏笔 → 查"伏笔"维度，核对埋设/揭示状态

**写作后回填（每次写完成都做）**：
1. 新出现的设定 → `entry set`
2. 状态变化的设定 → `entry append`（文本里写区间）
3. 反复出现的场景 → 建模入库：`entry add scene <名称>` + "场景模型"维度（收银台方位、货柜分布、动线等全部定好）
4. 埋设/揭示的伏笔 → 更新伏笔条目的状态与条件

## 示例

**场景建模**——主角常去的小镇超市：
```bash
python novel-cli/cli.py entry add scene 小镇超市
python novel-cli/cli.py type add dimension 场景模型 "空间布局、物件方位等固定描述"
python novel-cli/cli.py entry set 小镇超市 场景模型 布局 "（全书）入口朝南，收银台在入口右侧，三排货架：零食/日用品/生鲜，冷柜靠东墙"
python novel-cli/cli.py entry append 小镇超市 场景模型 布局 "（第6章起）重新装修：收银台移到入口正中"
python novel-cli/cli.py entry set 小镇超市 首现位置 引用 "首次出现：L3#12"
```

**伏笔记录**——早埋的伏笔：
```bash
python novel-cli/cli.py entry add concept 星痕印记
python novel-cli/cli.py type add dimension 伏笔 "伏笔的埋设/揭示状态与条件"
# 状态属性（当前值，open=已埋设未回收 / resolved=已回收）——写作时更新
python novel-cli/cli.py entry set 星痕印记 伏笔 状态 "open"
# 埋设/揭示条件、历史用其他键或多行描述
python novel-cli/cli.py entry append 星痕印记 伏笔 条件 "（第1-10章）仅手腕淡印，刻意遮挡"
python novel-cli/cli.py entry append 星痕印记 伏笔 条件 "揭示条件：林夜得知星核存在时浮现全貌"
```

### 伏笔状态约定

- **每个伏笔条目（concept 类型）的 `伏笔` 维度下必须有 `状态` 键**，值为当前状态：
  - `open`：已埋设，未回收（写作时应知道它还没兑现，避免提前失效）
  - `resolved`：已回收（写作时知道它已完成，避免重复使用）
- 写作中**埋设伏笔** → `entry set <伏笔名> 伏笔 状态 open`；**回收伏笔** → `entry set <伏笔名> 伏笔 状态 resolved`（可带回收位置，如 `resolved - 第X章`）
- 每次写作涉及伏笔前先 `entry get` 查状态：open 的伏笔可用/应推进，resolved 的不得再当悬念
- 埋设/揭示的**条件与历史**写在 `条件` 等键的多行描述里（区间用文本），与 `状态`（当前值）分离

## 名称映射（translation）——通用文本替换

**用户可能对 agent 起的名字不满意**（角色名、地名、道具名、专有名词、特定称谓等），不要等用户提出后全文替换——**从一开始就用占位符写作**，发布时自动替换为最终名；改名只改数据库一条记录。

**写作规范（必须遵守）**：创建任何**用户可能改名的实体**时，用 `{{原始名-类型}}` 占位符（原始名 = agent 起的名，类型后缀避免不同实体同名冲突），并 `translation add` 登记：

```bash
python novel-cli/cli.py translation add 林夜-主角 林夜 --note 主角
python novel-cli/cli.py translation add 青石镇-地点 青石镇
python novel-cli/cli.py translation add 星核-概念 星核
```

- **素材库条目名可直接用占位符形态**：`entry add character "{{林夜-主角}}"`——写作时引用该角色用 `{{林夜-主角}}`
- 梗概（L1-L4）与正文中引用该实体也用 `{{key}}`
- **发布时** `{{key}}` 替换为 display（`plot get` 查看梗概时也会显示替换后的文本）
- **改名**：`translation set <key> <新名>` → `translation apply`（批量重跑已发布正文，无需全文查找替换）
- 已运行项目**无缝兼容**：现有裸名条目照常；要对某实体启用改名机制时，把条目名与正文引用改为 `{{键}}` 形态即可，无需迁移其他数据

**★ 替换边界（必须明确）**：`{{key}}` → display 的替换**只发生在发布产出时**（`publish` 写 contents/、`translation apply` 重跑已发布正文）。**一切持久数据保持键**：数据库（条目名、节点标题）、梗概/正文 md 文件、素材库条目、`fact`/`log`/`context` 均**不被替换**——键只在最终产出文本中呈现为 display。`plot get` 仅是显示层呈现替换后文本，不改文件。不要在任何数据库/文件写入路径上应用替换。

命令速览：
```bash
python novel-cli/cli.py translation add <key> <display> [--note 说明]
python novel-cli/cli.py translation set <key> <display>   # ★ 改名
python novel-cli/cli.py translation list
python novel-cli/cli.py translation del <key>
python novel-cli/cli.py translation apply [--id 节点]      # 重跑已发布正文
```

## 查表时机

**每次写 L3 事件梗概或 L4 正文前必须查表**；写作中产生新信息**写完立即回填**。宁可多记，不可漏记——素材库是防止前后矛盾的第一道防线。
