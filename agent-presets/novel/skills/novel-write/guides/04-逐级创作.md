# 04 — 逐级创作规则

## 核心原则：逐级不跳，但允许部分推进

```
L1 全书梗概 ──确认──→ L2 分卷梗概 ──确认──→ L3 事件梗概 ──确认──→ L4 正文 ──确认──→ publish
```

**任何子节点的创建、编辑、修改、确认，都要求父节点已确认**（数据层强制，见 guide 03）。在用户明确确认当前层级的内容之前，不进入下一层级。

**允许部分推进**：不必等某个层级全部完成才进入下一级。例如：

- L1 确认后，先完成第一、二卷的 L2 并确认，就可以开始第一、二卷的 L3——第三卷的 L2 可以后补
- 第一卷的 L3 全部确认后即可进入第一卷的 L4，不必等第二卷的 L3
- 每个节点只依赖它的**父节点链**（到 L1），不依赖同级

## 为什么必须逐级

1. **上下文控制**：低层级内容量大，若在 L4 创作中回头改高层级规划，会导致与已完成正文的矛盾
2. **一致性保证**：上一层的决策约束下一层，防止剧情失控
3. **用户可控**：在梗概级别提出修改的成本远低于正文级别

## 确认的定义

以下任一算作"用户确认"：
- 用户明确说"可以""没问题""继续""进入下一级"等
- 用户对当前层级内容提出修改意见 → 修改后再次请求确认 → 用户认可
- 用户说"就这样，开始写下一级吧"

以下**不算**确认：
- 用户沉默
- 用户说"你先写着"但未评价当前层级的内容
- 用户切换到其他话题

## 查表规则

写 L3 或 L4 前，必须执行：
1. 列出当前事件涉及的所有角色/地点/道具/概念/场景模型/伏笔
2. 对每个涉及条目执行 `entry get <名称>`
3. 写作时严格遵循已记录设定；若发现设定缺失 → 先补充素材库，再继续写

## 修改与级联

**修改任何节点的正确姿势**：
1. 编辑该节点的 md 文件
2. 立即 `plot status <id> revised` 标记修改——这一步触发数据层的**级联失效**（见 guide 03）
3. 级联会自动把该节点的**后续同级 + 全部子树 + 引用网络**标为 `affected`

**忘记置 revised 的兜底（内容漂移检测）**：数据层记录每个节点最近一次"被认可"时的内容指纹（大小+hash）。如果直接改了文件没置 revised，`plot get` / `context` 会提示"内容漂移"，`plot list` 汇总漂移节点数；**`publish` 会拒绝**（confirmed 后文件被改）——必须先 `plot status revised` 标记修改、重新确认后才能发布。**规范：改完任何节点立即置 revised，不要依赖兜底。**

**affected 节点的处理**：内容没有被直接改，但前提变了（如前面的剧情被改写），需要核查衔接。核查方式：
- `plot list` / `novel_status` 会持续列出 affected 节点及其原因——这是**长期提醒**，可能多轮修改后才轮到处理它
- 核查后确认衔接无误 → `plot status <id> confirmed` 恢复（需祖先链确认）

## L4 正文创作流程

1. **创建 L4 节点**：挂到主事件 L3 下（`--parent <L3 id>`）；若本章穿插其他事件，用 `plot ref add <L4_id> <L3_id>` 存入数据库（次引用）
2. **组装上下文**：`context <id>`（父链/引用/事实账本/风格规则/前后章）+ 按涉及设定 `entry get` 核查条目（含场景模型、伏笔）
3. **写正文**：编辑 `novel-cli/plots/L4/{卷}/<章节>.md`（缓存工作区，按卷分目录）——**md 只写正文，不写入任何元数据**（发布产出干净）；落笔前对照[写作原则](08-写作原则.md)：冰山叙事——已知信息分散暗示、写事实不写结论、一次一个暗示（L3 规划时已布局的暗示点在此兑现）
4. **回填素材库**：文中产生的新设定/变化/伏笔 → `entry set` / `entry append`
4.5. **风格自查（写作后必做）**：对照风格库特征 + [去 AI 味清单](07-去AI味.md) 检查本章：删过度修饰/破四字格律、情绪落到动作细节、对话个性化、节奏有呼吸感；修改后复读对话段与情绪段
5. **用户确认后发布**：`plot status <id> confirmed` → `publish <id>`

**重要**：`plots/L4/` 是 agent 工作区，不是正式产出。用户确认后必须 `publish` 才能生成 `contents/` 下的正式文件；编号、路径、格式转换全由 `publish` 自动处理，不要手动操作 `contents/`。

## 行内指令（`<>` 约定）

**用户可在正文任意位置用 `<` 与 `>` 包围的区域插入写作指令**，例如：

```
她推开门，屋子里很安静。
<这里放慢节奏，写一段她环顾屋内的细节，暗示有人来过>
窗台上的灰被擦掉了一小块。
```

**规则**：

1. 指令是 `<` 和 `>` 之间的**整个区域**（单个尖括号对，不是 `<...></...>` 配对标签），内容为一句对写作方向的要求
2. 读到指令即按指令要求调整/补写正文（它可能是"放慢/加快节奏""暗示某设定""此处情绪转折"等）
3. **执行完毕后删除整个 `<>` 块（含尖括号）**——正文文件不残留任何指令痕迹；发布产出天然干净，无需另行清理
4. 指令与正文的关系：指令是"对这一段该怎么写的提示"，不是正文内容，也不是元数据——执行后即消失
5. 指令与素材库的关系：指令若要求写新设定/变化，正文产出后仍按常规回填素材库（`entry set` / `entry append`）

> 本约定是纯 agent 协作机制：用户使用自行承担后果。agent 侧只记住"读到就执行，执行完就删除"。

## 事实账本（已完成事项）

**每完成一个节点（确认或发布），记一条事实**——"这个节点让什么成了既成事实"：

```bash
python novel-cli/cli.py fact add "第5章完成：林夜得知星核存在" --category revealed --source 5
python novel-cli/cli.py fact add "老药师确认死亡" --category state_changed --source 5
```

**写作前必查**：`fact list`——"已完成事项勿重复写出"，防止把已发生的事再写一遍。

- `category`：`completed`（过程目标完成）/ `revealed`（信息已揭示）/ `state_changed`（不可逆状态变化）
- `--source` 记录"何时成了既成事实"（哪个节点）——**改动级联的反向定位依据**：改某节点时 `fact list --source <id>` 找到它确认过的事实，核查依赖这些事实的后续内容
- 事实必须来自**确认后的正文/梗概**；写前计划、章节义务不算事实

## 单节点创作（写作重心）

**拆树的目的就是减少单次创作的上下文长度——不要批量创作。**

1. **一次只填一个节点**：一次创作只写一个 L3 或一个 L4。禁止一次性填充多个节点。
2. **用户要求批量时** → 见下文"批量协作（子 Agent 并行）"
3. **衔接（双向）**：填完只关注与前一个同级节点的衔接（读前一个节点的结尾）；**写前也读下一个节点的规划**（下章前瞻），让本章结尾为下章自然铺垫。不回头检查父节点——子节点一般是在父节点基础上增添细节；如果发现内容超出了父节点的范围，**提醒用户/自己应该修改父节点，而不是在子节点里扩张**。
4. **省下来的资源投入精细创作**：
   - 复杂曲折的剧情 → 多审查几遍逻辑是否有问题
   - 情感集中爆发的部分 → 先设计好大致情节，可上网搜索别人的处理方式作参考
   - 固定场景中的剧情 → 先建模整个场景（反复出现的场景写入素材库，见 guide 02），防止前后描述冲突
   - 慢工出细活。

## 批量协作（子 Agent 并行）

**何时用**：仅限"已有数据的补写/修订"场景，或用户明确要求快速推进时。**首次创作（尚无正文）仍逐个填充**，保证剧情连贯性。

**批次分配**：
- 每批 5-8 个节点（按总数动态调整），**批次间不重叠**
- 批次内串行创作（保住连贯性），批次间并行执行

**子 Agent 规则**（每个子 Agent 的 prompt 必须包含）：
1. 每节点开始前必读：该节点的规划（L3 事件梗概 / L4 模板）+ 涉及素材库条目（`entry get`）
2. 只负责自己批次内的节点，**只更新自己负责的节点状态**
3. 严格按梗概的核心事件创作，不擅自改规划；发现规划问题 → 记录并报告，不自行扩张
4. 写完后执行风格自查 + [去 AI 味清单](07-去AI味.md)
5. 通过共享状态（`novel_status` / `log show`）感知全局进度，不重复认领

**并发安全**：批次不重叠 + 各子 Agent 只写自己的节点文件与状态 → 无写入冲突。

**完成后**：主 Agent 汇总各批次结果，运行 `validate` 完整性检查，再交给用户确认。

## 用户催促时的处理

如果用户要求跳过某个层级直接写正文：

> 提醒：跳级创作可能导致后续大幅返工。建议至少完成 L1 全书梗概的确认。是否确认跳过？

如果用户坚持 → 遵从，但在日志中记录"跳级操作"：
```bash
python novel-cli/cli.py log append 修订 跳级 "跳级操作" "用户要求跳过L2直接写L4"
```

## 回退修改

如果用户在高层级（如 L2）提出修改，而低层级（L3/L4）已有内容：
1. 提醒用户哪些已有内容可能受此次修改影响（`plot list` 会显示 affected）
2. 询问用户是否一并调整受影响内容
3. 修改高层级内容并置 `revised`（触发级联）
4. 按用户指示逐个修订受影响内容，修订后重新确认

## 设定冲突处理

**用户提出新的剧情/设定时，若与已有且用户未一并提到的剧情/设定冲突，不要盲目遵从。**

识别冲突后按三步处理：
1. **阐明冲突点与不合理之处**：明确说出新设定与哪些已有设定冲突（引用素材库条目/剧情节点），以及为什么不合理（如时间线矛盾、角色动机违背、世界规则破坏）
2. **向用户提问**，给出清晰选项：
   - **无视风险继续**（用户明确接受冲突，则照做并记录到日志）
   - **撤回新设定**（保留原设定，用户另提修改）
   - **其它解决方案**（提出折中/替代方案供用户选择）
3. 用户选择后再执行；**绝不自行决定**遵从或修改

**判断标准**：
- 冲突 = 新设定与**已有且未被用户本次提及**的设定矛盾（素材库条目、已确认的 L3/L4、已发布正文）
- 用户**明确提及**"改掉 XX"或"推翻 XX"时不算冲突——那是修改意图，走正常"置 revised + 级联"流程
- 把握不准是否冲突时，也先向用户确认，不要默认新设定覆盖旧设定
